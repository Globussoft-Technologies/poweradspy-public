# AdMob Lander Implementation

This document is the final working contract for the AdMob lander flow.

It is written for both PAS and DS, and it answers:

- what DS must send
- what PAS stores in SQL and Elasticsearch
- which fields are PAS-maintained
- how the 3 AdMob lander APIs behave
- how to finalize the existing SQL table and ES index to this contract

## Who should use this document

- DS team:
  - use this to know which API to call, in what order, and what payload to send
- PAS developers:
  - use this to understand storage shape, ownership boundaries, rollout scripts, and runtime behavior

## Scope

This work is AdMob-only.

We did not touch the legacy lander implementations for other networks.

The AdMob lander flow now lives under:

- `src/services/admob/landers/`
- `src/services/admob/insertion/`
- `scripts/admob/`

## Problem solved

Before this work, AdMob did not have a dedicated, payload-shaped lander pipeline for:

- final rendered lander HTML
- lander screenshot path
- outgoing redirect chain
- WhatsApp evidence found on the lander
- prefilled WhatsApp text
- multi-number / rotator detection
- first-analysis and last-analysis timestamps
- AdMob-app source context

Because of that, DS had no clean AdMob-specific place to send this data, and PAS had no reliable
way to store and index it consistently.

This implementation fixes that by providing:

- an AdMob-only `insert_html_content` API
- finalized SQL storage in `mob_ad_lander_content`
- daily pickup locking in `mob_ad_lander_claims`
- finalized ES projection inside `mob_search_mix`
- migration scripts to move the existing AdMob lander schema to the new contract

## Quick start

### DS quick start

Normal DS flow for one AdMob ad:

1. Call `GET /api/v1/admob/landers/get_ads_for_blackhat` with:
   - header `x-scraper-name`
   - query `status=0` for never-processed ads, or `status=2` for reprocessing older ads
   - use the returned `ad_id` value in every later lander API call for that ad
2. Optionally call `POST /api/v1/admob/landers/upload_admob_blackhat` if PAS/NAS must store the screenshot and ZIP generated by the crawler
3. Call `POST /api/v1/admob/landers/insert_html_content` with the finalized lander payload

### Developer rollout quick start

For a clean finalization of AdMob lander storage on an existing environment:

1. Reset polluted test state if needed:

```bash
node scripts/admob/requeue-lander-ads.js --reset-all --delete-lander-content --commit
```

2. Finalize the SQL schema:

```bash
node scripts/admob/migrate-lander-fields.js --drop-obsolete --commit
```

3. Rebuild the AdMob ES index so old lander fields disappear:

```bash
node scripts/admob/rebuild-search-index.js --commit
```

Use `apply-es-mapping.js` only when you want an additive ES mapping patch and do not want a full AdMob ES rebuild.

## End-to-end flow

This is the normal runtime lifecycle after rollout is complete:

1. PAS insertion already has the AdMob ad in `mob_ads` and `mob_search_mix`
2. DS calls `get_ads_for_blackhat`
3. PAS:
   - filters by `status=0` or `status=2`
   - checks ES presence
   - prevents same-day duplicate pickup using `mob_ad_lander_claims`
   - marks the selected ad as fetched
4. DS analyzes the landing page and gathers:
   - rendered HTML
   - screenshot path
   - outgoing redirects
   - WhatsApp evidence
   - campaign id if available
5. DS optionally uploads screenshot and ZIP assets through `upload_admob_blackhat`
6. DS sends the final lander payload to `insert_html_content`
7. PAS:
   - validates and normalizes the payload
   - updates `mob_ads.redirect_status`
   - upserts `mob_ad_lander_content`
   - completes the daily claim row
   - rebuilds the AdMob ES document from SQL
   - queues ES retry if immediate indexing fails

## Ownership

### DS provides

DS should send the final lander analysis payload with:

- `ad_id`
- `platform`
- `destinations`
- `html_path`
- `screen_shot`
- `html_content`
- `domain_registered_date`
- `domain_age`
- `country_iso`
- `outgoing_url`
- `redirects`
- `whatsapp`
- `campaign_id`
- `created`
- `updated`

DS may also send:

- `status` or `lander_status`
- `lead_campaign_tag`
- `post_owner`

If DS sends `post_owner`, it must be a real advertiser name.

Important:

- in the AdMob lander APIs, DS-facing `ad_id` means the PAS internal SQL id returned by `get_ads_for_blackhat`
- DS should not send the public AdMob ad id back to PAS

Do not send placeholder values such as:

- `NA`
- `N/A`
- `None`
- `null`

DS should not send duplicate helper fields that represent the same thing.

Examples:

- do not send `source_app` or `source_website` in AdMob lander payloads
- send `whatsapp[].url`, not a second duplicate WhatsApp URL field
- send the final normalized payload shape shown below whenever possible

### PAS provides

PAS handles:

- payload validation
- MySQL upsert into `mob_ad_lander_content`
- same-day pickup locking through `x-scraper-name`
- ES document rebuild/index for the AdMob ad
- `redirect_status` transitions on `mob_ads`
- conditional AdMob owner backfill when DS sends `post_owner` and the ad still has no owner
- WhatsApp rotator detection from stored phone numbers
- `whatsapp_rotator_count`
- `whatsapp_rotator_detected`
- default `lead_campaign_tag` when rotator evidence exists and DS does not send a tag

## Important contract rules

### 0. `ad_id` in the lander APIs is the PAS internal SQL id

For the AdMob lander APIs only:

- PAS returns the internal SQL row id inside the `ad_id` field of `get_ads_for_blackhat`
- DS should send that same `ad_id` value back to:
  - `upload_admob_blackhat`
  - `insert_html_content`

Why this exists:

- DS does not need the public AdMob ad id
- PAS can safely use its own stable row id for lander screenshots, ZIP paths, and SQL updates
- this prevents public AdMob ids from leaking into NAS file paths or scraper payloads

The public AdMob ad id still exists inside PAS and Elasticsearch, but it is no longer part of the DS-facing lander contract.

### 1. `platform` identifies the crawler

For AdMob lander ingestion, `platform` is the crawler identifier, not the ad network platform.

Example:

- `12` = Python crawler

The insert API requires `platform`.

Legacy `crawled_by` should not be used anymore for AdMob DS payloads.

### 2. Do not send `source_app` or `source_website`

AdMob insertion already owns the real top-level ES `source_app` dimension.

So the AdMob lander contract intentionally does not use:

- `source_app`
- `source_website`

If DS sends `source_app` anyway, PAS ignores it during lander insertion.

### 3. `created` and `updated`

- `created` = first time the lander analyzed the ad
- `updated` = every time the lander analyzes the ad, including the first time

PAS now keeps the lander row updated even when the incoming lander status is `3`, so these fields
stay meaningful for every analysis attempt.

### 4. PAS-maintained rotator fields

PAS now maintains:

- `whatsapp_rotator_count`
- `whatsapp_rotator_detected`
- default `lead_campaign_tag`

Current PAS rule:

- collect distinct WhatsApp phone numbers from `whatsapp[]`
- if distinct phone count is greater than `1`:
  - `whatsapp_rotator_detected = true`
  - `whatsapp_rotator_count = distinct phone count`
  - `lead_campaign_tag = "high-volume-lead-campaign"` only if DS did not send a tag

### 5. No repeated fields

The finalized AdMob lander contract keeps only one field per purpose.

Examples:

- nested WhatsApp link is stored as `whatsapp[].url`
- we do not keep top-level duplicate fields like `whatsapp_url`, `whatsapp_phone`, `whatsapp_message`
- we do not keep `source_website`
- we do not keep `raw_payload_json`

### 6. Optional `post_owner` only backfills the actual ad owner

DS may optionally send:

- `post_owner`

This field is not stored in `mob_ad_lander_content`.

Instead, PAS uses it only to enrich the actual AdMob ad when the ad still has no owner attached.

Current behavior:

- if the AdMob ad has no owner yet:
  - PAS creates or reuses the `mob_post_owners` row
  - PAS sets `mob_ads.post_owner_id`
  - PAS rebuilds ES so the ad document gets `post_owner`
- if the AdMob ad already has an owner:
  - PAS does not overwrite it
  - lander insertion continues normally

Validation rules:

- if `post_owner` is omitted or `null`, PAS ignores it
- if `post_owner` is sent, it must be a non-empty string
- placeholder values such as `NA`, `N/A`, `None`, and `null` are rejected

### 7. One ad can only be picked once per day

PAS now prevents same-day duplicate pickup across multiple DS devices.

The GET API requires:

- `x-scraper-name` header
- `status=0` or `status=2`

PAS stores a same-day claim row in `mob_ad_lander_claims` when an ad is handed out.

That means:

- the same ad cannot be returned to a second crawler on the same day
- the same ad can be returned again on a later day
- PAS records which scraper claimed it

### 8. GET `status` meanings

For `GET /landers/get_ads_for_blackhat`:

- `status=0` -> ads never processed by landers
- `status=2` -> ads processed earlier, ordered from oldest `updated` to newest, excluding ads processed on the current day

## Status glossary

This flow uses multiple fields named `status`, but they do not all mean the same thing.

That is the main reason this part feels confusing.

The safest way to understand it is:

- GET `status` = queue selector
- insert `lander_status` = DS lander result
- upload `status` = NAS folder selector
- `redirect_status` = PAS internal pipeline state

### 1. GET `status` in `get_ads_for_blackhat`

This is a fetch filter.

DS sends this when asking PAS for ads to process.

Allowed values:

- `0`
- `2`

Meaning:

- `status=0` means: give me ads that have never been processed by landers
- `status=2` means: give me ads that were processed earlier and can be reprocessed now

Important:

- this is not the lander result
- this is not stored in `mob_ad_lander_content.lander_status`
- this only decides which ads PAS should return now

PAS stores this in `mob_ad_lander_claims.requested_status` for tracking.

### 2. `status` or `lander_status` in `insert_html_content`

This is the lander result sent by DS while saving the final lander payload.

Allowed values:

- `1`
- `2`
- `3`

Important:

- inside `insert_html_content`, `status` and `lander_status` mean the same thing
- PAS accepts both field names as input aliases
- PAS normalizes both to one stored field: `lander_status`

Why PAS accepts both:

- some DS payloads naturally send a generic `status`
- PAS stores the lander result in its own field named `lander_status`
- this avoids mixing the DS lander result with PAS internal `redirect_status`

Recommended DS usage:

- use `lander_status` in `insert_html_content`

That keeps the payload much clearer than a generic `status`.

Current behavior:

- if DS sends no `status` or `lander_status`, PAS defaults it to `1`
- `1` and `2` both follow the normal full-save path
- `3` is special:
  - HTML artifacts are not required
  - PAS still updates the lander row
  - PAS still updates timestamps and workflow state

#### What `1`, `2`, and `3` mean for the insert API

Intended business meaning:

- `1` = BLACKHAT found
- `2` = WHITEHAT found
- `3` = no response / no usable lander result

In simple language:

- `1` means DS successfully analyzed the lander and considers it a BLACKHAT result
- `2` means DS successfully analyzed the lander and considers it a WHITEHAT result
- `3` means DS attempted the lander but did not get a usable response

Current AdMob behavior in PAS:

- `lander_status = 1`
  - treated as a normal successful lander save
  - `html_path`, `screen_shot`, and `html_content` are required
  - PAS stores `mob_ad_lander_content.lander_status = 1`
  - PAS sets:
    - `redirect_status = 4` for Python crawler (`platform = 12`)
    - `redirect_status = 1` for non-Python crawler

- `lander_status = 2`
  - treated as a normal successful lander save
  - `html_path`, `screen_shot`, and `html_content` are required
  - PAS stores `mob_ad_lander_content.lander_status = 2`
  - PAS sets:
    - `redirect_status = 4` for Python crawler (`platform = 12`)
    - `redirect_status = 1` for non-Python crawler

- `lander_status = 3`
  - treated as the no-response case
  - `html_path`, `screen_shot`, and `html_content` are not required
  - PAS still stores / updates the lander row
  - PAS still updates timestamps and claim state
  - PAS sets:
    - `redirect_status = 6` for Python crawler (`platform = 12`)
    - `redirect_status = 3` for non-Python crawler

Important note:

- in AdMob, `1` and `2` are different DS result labels, but both are part of the same normal successful-save path in PAS
- PAS does not create separate SQL tables or separate redirect workflows for BLACKHAT vs WHITEHAT
- the main special case is `3`

Recommended DS convention:

- use `lander_status` in `insert_html_content`
- keep upload `status` and insert `lander_status` logically aligned

Example:

- if upload API uses `status = 2` so files go to the WHITEHAT folder
- insert API should also use `lander_status = 2`

### 3. `status` in `upload_admob_blackhat`

This is only a folder selector for NAS upload.

Allowed values:

- `1` = `BLACKHAT`
- `2` = `WHITEHAT`

Important:

- this does not mean lander result
- this does not control SQL lander storage
- this does not control `redirect_status`

It only decides where the uploaded files are stored.

### 4. `redirect_status` in `mob_ads`

This is PAS internal workflow state.

DS should not send this field.

PAS updates it automatically while the AdMob lander flow moves forward.

Current values:

- `0` = pending for lander pickup
- `2` = fetched by `get_ads_for_blackhat` and found in ES
- `5` = fetched by `get_ads_for_blackhat` but missing in ES
- `1` = insert completed for non-Python crawler and `lander_status != 3`
- `3` = insert completed for non-Python crawler and `lander_status = 3`
- `4` = insert completed for Python crawler (`platform = 12`) and `lander_status != 3`
- `6` = insert completed for Python crawler (`platform = 12`) and `lander_status = 3`

The key point is:

- `lander_status` tells PAS what result DS is sending
- `redirect_status` tells PAS where the ad is in the PAS processing pipeline

### One example from start to finish

1. An AdMob ad exists in PAS and has:
   - `redirect_status = 0`
2. DS calls:
   - `GET /get_ads_for_blackhat?status=0`
3. PAS returns the ad and updates:
   - `redirect_status = 2`
4. DS finishes analysis and sends:
   - `POST /insert_html_content`
   - `lander_status = 2`
5. PAS stores:
   - `mob_ad_lander_content.lander_status = 2`
6. PAS also updates:
   - `redirect_status = 4` if `platform = 12`
   - `redirect_status = 1` for a non-Python crawler

So in that same flow:

- GET `status=0` meant which ads to fetch
- insert `lander_status=2` meant the DS lander result
- `redirect_status=4` meant PAS completed the Python crawler path internally

### Recommended DS convention

To keep things simple:

- use `status` only in `get_ads_for_blackhat`
- use `lander_status` in `insert_html_content`
- use `status` in `upload_admob_blackhat`
- never send `redirect_status`

## API inventory

The AdMob lander routes are:

- `GET /api/v1/admob/landers/get_ads_for_blackhat`

## 1. `GET /api/v1/admob/landers/get_ads_for_blackhat`

### Purpose

Returns AdMob ads that are waiting for lander processing.

It reads from SQL, checks the AdMob ES index in batch, and creates a same-day claim so another
DS device does not receive the same ad again on that day.

This API is only for fetching work.

It does not store lander HTML, screenshot, or WhatsApp evidence.

### Current selection logic

The API now requires:

- header `x-scraper-name`
- query/body `status=0` or `status=2`

Selection behavior:

- `status=0`
  - return ads with no row in `mob_ad_lander_content`
  - exclude ads already claimed today in `mob_ad_lander_claims`
- `status=2`
  - return ads with an existing lander row
  - use `mob_ad_lander_content.updated` oldest to newest
  - exclude ads already processed today
  - exclude ads already claimed today

For returned ads:

- PAS creates a same-day claim row in `mob_ad_lander_claims`
- PAS sets `mob_ads.redirect_status = 2`

For ES misses:

- PAS sets `mob_ads.redirect_status = 5`
- the ad is not returned

### Request

```http
GET /api/v1/admob/landers/get_ads_for_blackhat?status=0
x-scraper-name: crawler-device-01
```

Request rules:

- `x-scraper-name` is mandatory
- `status` accepts only `0` or `2`
- optional `limit` may be sent, but PAS clamps it to the service max

### Success response example

```json
{
  "code": 200,
  "message": "Ads fetched successfully",
  "data": [
    {
      "id": 123,
      "ad_id": 123,
      "destination_url": "https://example-landing.com/whitehat",
      "country": ["US", "CA"]
    }
  ],
  "exe_time": 0.012
}
```

### Validation failure examples

```json
{
  "code": 422,
  "message": "The x-scraper-name header is required.",
  "data": [],
  "details": {
    "hint": "Send the crawler/device identity in the x-scraper-name header so PAS can prevent same-day duplicate pickup."
  }
}
```

```json
{
  "code": 422,
  "message": "The status filter is invalid.",
  "data": [],
  "details": {
    "hint": "Use status=0 for never-processed ads or status=2 for previously processed ads."
  }
}
```

### Other responses

```json
{
  "code": 200,
  "message": "No Ads found",
  "data": [],
  "exe_time": 0.003
}
```

```json
{
  "code": 200,
  "message": "Ads not found in Elasticsearch",
  "data": [],
  "exe_time": 0.008
}
```

```json
{
  "code": 503,
  "message": "The AdMob Elasticsearch connection is unavailable.",
  "data": [],
  "exe_time": 0.001
}
```

## 2. `POST /api/v1/admob/landers/upload_admob_blackhat`

### Purpose

Uploads the media and ZIP assets generated by the lander job to NAS storage.

This endpoint does not save the lander payload into SQL.

This API is only for file upload / NAS storage.

It does not save the final lander analysis contract.

### Request

Content type:

- `multipart/form-data`

Accepted form fields:

- `ad_id`
- `status`
- `country_iso` or `country`
- `media` file
- `zip` file

`status` rules for this upload API:

- `1` -> BLACKHAT folder
- `2` -> WHITEHAT folder

### Example request

```http
POST /api/v1/admob/landers/upload_admob_blackhat
Content-Type: multipart/form-data

ad_id=2084
status=2
country_iso=IN
media=@lander.png
zip=@lander.zip
```

### Success response example

```json
{
  "code": 200,
  "message": "files are stored successfully",
  "id": 2084,
  "country": "IN",
  "image_path": "/pas-dev/stream/admob/whiteHatAd/202608/2084.png",
  "html_path": "/pas-dev/stream/admob/whiteHatAd/202608/2084.zip"
}
```

### Common failure responses

```json
{
  "code": 404,
  "message": "no file found"
}
```

```json
{
  "code": 400,
  "message": "status must be 1 (blackhat) or 2 (whitehat)"
}
```

## 3. `POST /api/v1/admob/landers/insert_html_content`

### Purpose

This is the main AdMob lander ingestion API.

It:

1. validates the payload
2. locks the AdMob SQL row
3. updates `mob_ads.redirect_status`
4. upserts `mob_ad_lander_content`
5. rebuilds and writes the AdMob ES document
6. queues ES retry if indexing fails after SQL commit

This is the API that saves the lander analysis contract.

### Accepted body wrappers

The API accepts any of these body shapes:

- one plain object
- one object wrapped inside `insertData`
- `{ "ads": [ ... ] }`
- a raw array

Recommended DS format:

- send one object wrapped inside `insertData`
- keep the inner `insertData` object aligned with the canonical payload shape shown earlier

### Required fields

For normal lander saves:

- `ad_id`
- `platform`
- `destinations`
- `html_path`
- `screen_shot`
- `html_content`

For `status = 3` or `lander_status = 3`, HTML artifacts are not required.

### Example request

This example shows the wrapped API body, not a second payload contract.

`insertData` is just the canonical payload object wrapped inside the accepted request body shape.

## `redirect_status` lifecycle

Current AdMob lander status transitions are:

- `0` = pending for lander pickup
- `2` = fetched by `get_ads_for_blackhat` and found in ES
- `5` = fetched by `get_ads_for_blackhat` but missing in ES
- `1` = lander insert completed for non-Python crawler and `status != 3`
- `3` = lander insert completed for non-Python crawler and `status = 3`
- `4` = lander insert completed for Python crawler (`platform = 12`) and `status != 3`
- `6` = lander insert completed for Python crawler (`platform = 12`) and `status = 3`

Current insert rule:

- if `platform = 12`:
  - `status 1/2` -> `redirect_status = 4`
  - `status 3` -> `redirect_status = 6`
- otherwise:
  - `status 1/2` -> `redirect_status = 1`
  - `status 3` -> `redirect_status = 3`

## Final SQL storage

The finalized AdMob lander SQL table is `mob_ad_lander_content`.

Final columns:

- `ad_id`
- `platform`
- `lander_status`
- `destinations`
- `html_path`
- `screen_shot`
- `html_content`
- `domain_registered_date`
- `domain_age`
- `country_iso_json`
- `outgoing_url_json`
- `redirects_json`
- `whatsapp_json`
- `campaign_id`
- `whatsapp_rotator_detected`
- `whatsapp_rotator_count`
- `lead_campaign_tag`
- `created`
- `updated`

The new same-day claim table is `mob_ad_lander_claims`.

Claim columns:

- `ad_id`
- `process_date`
- `scraper_name`
- `requested_status`
- `claimed_at`
- `completed_at`
- `last_lander_status`
- `created_at`
- `updated_at`

Notes:

- `country_iso_json`, `outgoing_url_json`, and `redirects_json` remain JSON-text SQL columns
- `whatsapp_json` stores the normalized WhatsApp evidence array
- optional `post_owner` does not live in `mob_ad_lander_content`; PAS uses it only to fill `mob_ads.post_owner_id` through `mob_post_owners` when that relation is still missing
- top-level helper fields such as `whatsapp_url`, `whatsapp_phone`, `source_website`, and `raw_payload_json` are no longer part of the final schema
- `mob_ad_lander_claims` is what prevents two DS crawlers from receiving the same ad on the same calendar day

## DS dependencies

For DS to use the AdMob lander flow correctly:

1. The AdMob ad must already exist in PAS insertion data.
2. DS must fetch ads from `get_ads_for_blackhat` with:
   - `x-scraper-name`
   - `status=0` or `status=2`
3. DS must upload screenshot / ZIP assets if NAS storage is needed.
4. DS must call `insert_html_content` with the finalized payload.
5. DS should send every distinct WhatsApp evidence row it sees in `whatsapp[]`.

What DS should not rely on:

- PAS inferring a rotator from one phone number
- PAS keeping legacy AdMob lander helper fields forever
- `crawled_by` as the crawler identifier
- `source_app` or `source_website` as AdMob lander-owned identifiers

## PAS implementation dependencies

This flow depends on:

- AdMob MySQL being available
- AdMob ES index being available for `get_ads_for_blackhat`
- AdMob ES write access being available for immediate index refresh

If ES indexing fails after SQL commit:

- PAS keeps the SQL write
- PAS queues ES retry in `mob_es_outbox`
- the API responds with `mysql_saved = true`, `elastic_indexed = false`, `es_retry_queued = true`

## Migration and rollout

Because AdMob already had a live SQL table and ES index, rollout is split into migration scripts.

### Recommended order on an existing AdMob environment

If old test data already polluted SQL and/or ES docs, use this order:

1. Reset AdMob lander test state:

```bash
node scripts/admob/requeue-lander-ads.js --reset-all --delete-lander-content --commit
```

2. Finalize the SQL schema:

```bash
node scripts/admob/migrate-lander-fields.js --drop-obsolete --commit
```

3. Rebuild the AdMob ES index from the final mapping:

```bash
node scripts/admob/rebuild-search-index.js --commit
```

Why this order:

- step 1 makes all ads eligible again for lander pickup
- step 2 finalizes MySQL storage to the new contract
- step 3 recreates ES from current SQL so obsolete lander fields disappear cleanly

### SQL migration

Dry run:

```bash
node scripts/admob/migrate-lander-fields.js
```

Apply additive finalized columns:

```bash
node scripts/admob/migrate-lander-fields.js --commit
```

Finalize the lander SQL table and drop obsolete lander-only columns:

```bash
node scripts/admob/migrate-lander-fields.js --drop-obsolete --commit
```

Strict cleanup mode now:

- backfills `platform`
- normalizes legacy WhatsApp rows into `whatsapp_json`
- renames legacy nested `path` values into stored `url`
- recomputes PAS-maintained rotator fields
- backfills `created` and `updated`
- creates the same-day claims table used by the GET API
- drops deprecated lander-only columns after backfill, including the obsolete lander-side `source_app`

### ES mapping

If the live ES index only needs additive finalized lander fields:

```bash
node scripts/admob/apply-es-mapping.js --commit
```

If the live ES index must exactly match the finalized AdMob lander contract and old lander fields
should disappear:

```bash
node scripts/admob/rebuild-search-index.js --commit
```

Use the rebuild flow when removing old ES lander fields, because `PUT _mapping` cannot delete them.
